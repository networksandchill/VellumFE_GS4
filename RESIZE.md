# RESIZE.md — Adaptive Layout Scaling: Analysis & Plan

> **⚠️ This is a PLANNING / ANALYSIS document, not an implementation.**
>
> Nothing here has been built. It records *why* the current resize behavior
> degrades and *what direction* a real fix should take (Option D — an
> intent-first / fractional layout model). Code blocks below are **illustrative
> sketches**, not patches to apply verbatim.
>

---

## TL;DR

Adaptive scaling on terminal resize **already exists and already fires** (confirmed
in debug logs; Ghostty delivers resize events fine via crossterm `Event::Resize`).
The problem is not "build it" — it's that the automatic path produces worse results
than the manual `.reload` + `.resize` workflow, and the scaling only looks good
*near the terminal size the layout was authored at*.

Root cause: the layout stores window geometry as **absolute terminal cells** tied to
one design size. The user's *intent* (relative proportions, anchors, fill) is
discarded at author time, so every scaling algorithm is forced to reconstruct that
intent from the flattened cells — which is lossy, ambiguous, and non-invertible. The
correct fix (Option D) is to **store the intent and recompute geometry every frame**,
rather than keep guessing the inverse.

---

## The derivation: it's a normalization problem, not a scaling problem

### Step 1 — What the data model stores

`WindowDef` (`config.rs:289`) stores geometry as **absolute terminal cells**:

```rust
pub row: u16,    // Starting row position (0-based)
pub col: u16,    // Starting column position (0-based)
pub rows: u16,   // Height in rows
pub cols: u16,   // Width in columns
```

And `Layout` (`config.rs:644`) tags the whole set with the *one* terminal size those
cells were valid for:

```rust
pub terminal_width: Option<u16>,   // Designed terminal width (for resize calculations)
pub terminal_height: Option<u16>,  // Designed terminal height
```

The comment says it out loud: these exist "for resize calculations." That's the tell —
**the model must remember the size its own coordinates were authored at**, because the
coordinates are meaningless without it.

### Step 2 — Name the lost quantity

What the user actually *means* — "main is the left ~60%, the status bar is pinned to
the bottom 3 rows, the side panel is a fixed 30 cols on the right" — call that
**intent `I`**. The screen you want is a pure function of intent and current size:

```
target(s) = render(I, s)
```

But the layout file never stores `I`. It stores one already-rendered sample:

```
G(s₀) = render(I, s₀)        // the absolute cells at the design size s₀
```

`I` was discarded the moment the layout was flattened to cells. **That discard is the
root cause.** Everything downstream copes with it.

### Step 3 — Every fix is trying to invert a non-invertible function

Because `I` is gone, to support a new size `s₁` the code must compute it from the
sample:

```
G(s₁) = scale( G(s₀), s₀, s₁ )
```

For that to ever be correct, `scale` must satisfy
`scale(render(I,s₀), s₀, s₁) = render(I, s₁)` — i.e. it must **recover `I` from
`G(s₀)` and re-render**. Two independent reasons that's impossible:

**(a) `render(·, s₀)` is not injective.** At width 154, "fixed 92 cols" and
"fill ~60% of the width" both produce `cols = 92`. Same sample, different intent,
different correct answer at width 200. No function of `G(s₀)` alone can tell them
apart. So the code *guesses* intent from `widget_type` — that is the entire purpose
of the static/scalable classification in `apply_proportional_resize2`
(`app.rs:1985`):

```rust
"compass" | "injury_doll" | "dashboard" | "indicator" => { static_both.insert(...); }
"progress" | "countdown" | "hands" | ... | "command_input" => { static_height.insert(...); }
_ => {}   // everything else is "scalable"
```

That heuristic is standing in for the intent that was thrown away.

**(b) `render(·, s₀)` is lossy, so `scale` is not numerically invertible.** Two lossy
steps:

*Rounding* — `scale_to_terminal_size` (`config.rs:1894`):
```rust
window.cols = (window.cols as f32 * scale_x).round() as u16;
```

*Clamping* to the min-size floors in `widget_min_size` (`app.rs:1651`, `(5,3)` for
text, etc.), applied in `apply_height_resize` (`app.rs:1760`):
```rust
let mut new_rows = (*orig_rows as i32 + adjustment).max(min_constraint as i32) as u16;
```

Concrete round-trip proving non-invertibility — a 4-row text window, design height 49,
shrink to 18, grow back to 49:

```
49 → 18:  round(4 * 18/49) = round(1.47) = 1  → clamp to min 3  → stored rows = 3
18 → 49:  round(3 * 49/18) = round(8.16) = 8  → rows = 8
```

Started at 4, ended at 8 after a shrink-then-restore. `scale ∘ scale⁻¹ ≠ identity`.
The information needed to return to 4 was destroyed by `.max(3)`; no cleverness in the
scaler recovers it.

### Step 4 — The loss is persisted and re-consumed, so it compounds

It would be survivable if the lossy output were thrown away. It isn't.
`auto_scale_layout` writes the scaled result back as the new source of truth
(`app.rs:2029`):

```rust
self.layout.save_auto(char_name, &base_name, Some((width, height)))
```

So next session that degraded sample *is* `G(s₀)`. The pipeline is a feedback loop:

```
design → cells → scaled cells → saved as new design → scaled again → …
```

This is why the debug log shows the baseline wandering between sessions
(`baseline=87x9`, then `baseline=154x49`), and why `.reload` feels better:
`reload_windows` (`app.rs:3957`) reaches past the polluted sample and reloads the
pristine `layouts/<base>.toml`, momentarily restoring a clean `G(s₀)`.

### Step 5 — `calculate_layout` can't compensate

The per-frame placer (`window_manager.rs:1154`) is a **clipper, not a solver**. Its
only response to "this window doesn't fit" is truncate or drop (`window_manager.rs:1173`):

```rust
if x >= buffer_right || y >= buffer_bottom {
    // SKIPPING window ... outside buffer bounds
    continue;
}
```

It has no concept of "fill the rest" or "keep the ratio," so it cannot fix a bad
scale — it can only make widgets vanish. The intelligence has to live upstream, in
something that knows `I`.

### Step 6 — Why Option D dissolves the whole class

Options A/B/C (improve baseline handling / unify on ratio scaling / add anchoring) are
all different approximations of the impossible inverse in Step 3 — better guesses at
`scale`. Option D removes the need for `scale` entirely by storing `I` and computing
`render(I, s)` fresh every frame:

```
keep I  ⇒  G(s) = render(I, s)   // pure, total, recomputed from f.area() each draw
```

The moment you do that, the subsystem built to fake the inverse becomes dead code:
`auto_scale_layout`, `apply_proportional_resize2` / `apply_height_resize` /
`apply_width_resize` (~300 lines, `app.rs:1663–1975`), `scale_to_terminal_size`,
`baseline_layout`, `baseline_snapshot`, autosave-on-resize, and the scaling purpose of
`ResizeDebouncer`. No baseline to pollute, no drift to accumulate, no
`terminal_width`/`terminal_height` tag needed, no round-trip loss — because there is no
round trip.

> **You can't fix a normalization problem with smarter denormalization heuristics; you
> fix it by storing the normalized form.**

### Step 7 — The clincher: ratatui already ships `render(I, s)`

`render(I, s)` is just a constraint solver, and the project already links one.
`ratatui::layout::Layout` with `Constraint::{Percentage, Ratio, Min, Max, Fill, Length}`
*is* that function. `apply_width_resize` / `apply_height_resize` are a hand-rolled,
stateful, lossy reimplementation of it. Option D is not "write a new layout engine" —
it's "delete the homemade one and call the framework's."

## Code sketches (illustrative — NOT patches)

**Intent-first data model** (replaces the absolute-cell fields):

```rust
/// One axis of intent. Cells = fixed; the rest scale with the terminal.
enum Extent {
    Cells(u16),     // fixed: status bar = 3 rows, side panel = 30 cols
    Fraction(f32),  // share of the parent: main = 0.6
    Fill(u16),      // weighted share of leftover space (flex grow)
}

enum Edge { Start(Extent), End(Extent) } // pin to top/left or bottom/right

struct WindowDef {
    name: String,
    widget_type: String,
    x: Edge, y: Edge,             // anchor + offset, instead of raw col/row
    width: Extent, height: Extent,
    min_cols: u16, min_rows: u16, // a viewport floor, NOT a stored coordinate
    // ... all styling fields stay exactly as they are
}
```

**`G(s) = render(I, s)` — the pure resolver that replaces all scaling code:**

```rust
fn resolve(window: &WindowDef, area: Rect) -> Option<Rect> {
    let w = match window.width {
        Extent::Cells(c)    => c,
        Extent::Fraction(f) => (area.width as f32 * f).round() as u16,
        Extent::Fill(_)     => /* solved together with siblings */ unreachable!(),
    };
    let h = /* same for height */ todo!();
    let x = match window.x {
        Edge::Start(off) => area.x + off_to_cells(off, area.width),
        Edge::End(off)   => area.right().saturating_sub(off_to_cells(off, area.width) + w),
    };
    let y = /* same for y */ todo!();

    // Below a usable size, clip — never clamp-and-persist (Step 3b).
    let w = w.min(area.right().saturating_sub(x));
    let h = h.min(area.bottom().saturating_sub(y));
    (w >= window.min_cols && h >= window.min_rows).then(|| Rect::new(x, y, w, h))
}
```

The whole frame becomes "resolve against `f.area()`" — no `s₀`, no delta, no baseline,
no save:

```rust
terminal.draw(|f| {
    for win in &self.layout.windows {
        if let Some(rect) = resolve(win, f.area()) {
            render_window(win, rect, f.buffer_mut());
        }
    }
});
```

**Or lean entirely on ratatui's solver** for a column of windows — this *is*
`render(I, s)`, lossless and recomputed every draw:

```rust
use ratatui::layout::{Layout, Direction, Constraint};

let rows = Layout::default()
    .direction(Direction::Vertical)
    .constraints([
        Constraint::Fill(1),       // main: takes the leftover
        Constraint::Length(3),     // roundtime/vitals: fixed 3 rows
        Constraint::Length(1),     // command input: pinned bottom
    ])
    .split(f.area());              // f.area() = current terminal — adapts for free
```

**Why this passes the Step 3 round-trip test the current model fails:** intent
`Fraction(0.6)` resolves to `round(0.6 * w)` independently at *every* width — 154 → 92,
18 → 11, 154 again → 92. There is no stored intermediate to round off of and no
`.max(min)` baked into the saved value, so 154 → 18 → 154 returns exactly 92. The clamp
only ever happens at *render* time as a viewport floor; it is never written back, so it
cannot corrupt the source. That is the property A/B/C structurally cannot provide.

## Scope / cost of Option D (honest accounting)

Deletes more than it adds, but it is a real migration:

- **Schema change** to `WindowDef` geometry fields (`config.rs:289`).
- **Rewrite** the window editor's geometry inputs (it edits `Extent`/`Edge` now, not
  raw cells).
- **Rewrite** the mouse move/resize handlers in `app.rs` (drag edits intent, not
  absolute position).
- **One-time converter** from existing absolute `layout.toml` files → intent form.
- **Delete** the scaling subsystem listed in Step 6 once the resolver is in place.

Net effect: removes an entire category of bug rather than tuning it.
